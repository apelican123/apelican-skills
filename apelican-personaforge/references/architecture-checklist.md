# 架构决策清单

## 输入分类 → 默认实现

| 已有能力 | 4.0 默认做法 | 主要检查 |
|---|---|---|
| REST API | 翻译为任务型 MCP 工具（零依赖模板 `REST_TOOLS`） | 参数、分页、错误、结构化结果 |
| 单个 MCP | 透传代理 + 注入上游密钥 + 路径令牌校验（`MCP_UPSTREAM`） | 传输、session、元数据、认证 |
| 多个 MCP | 聚合目录 + 来源命名 + 静态只读 allowlist | 来源路由、allowlist、缓存、故障隔离 |
| 本机/内网 MCP | 建议 OpenAI Secure MCP Tunnel，不走 Cloudflare | 本机可达、工作区关联、非公开用途 |

## 多 MCP 设计（4.0 铸造版）

1. 每个上游分配稳定来源 ID；工具名使用 `<来源>:<工具>` 内部键；
2. 上游没有可信副作用注解时，不根据名称自动判定只读；
3. 允许执行的工具进入静态只读 allowlist；上游新增工具默认待审核；
4. 工具目录过大时，向 ChatGPT 暴露目录搜索与受控只读执行入口（`tools/list` 只给两个入口）；
5. 写操作逐个注册，不能经通用只读执行器绕过权限提示；
6. 每个上游独立管理 `mcp-session-id`；失效最多重建一次；
7. 工具目录缓存有 TTL；并发、超时、请求体和响应体有硬上限；
8. 单个来源失败时明确报告不可用来源，不伪装成完整成功。

## 工具压缩判断

不使用固定数字冒充平台上限。只要工具数量、相似描述或 schema 总量已经降低模型选择准确率，就考虑压缩。判断信号：ChatGPT 在验收时频繁选错工具、工具描述高度雷同、schema 总字节数过大。

参考案例：一个真实的四路资料聚合案例从 54 个上游工具压缩为两个入口（目录搜索与静态 allowlist 只读执行）。这只证明该结构在当时任务中合理，不代表所有服务都必须使用两个工具。

## 输出架构图文字版

```text
ChatGPT
  -> 统一 MCP 工具面（/u/<令牌>/mcp，路径令牌校验）
  -> 来源路由 + 静态 allowlist
  -> 各上游 MCP / REST API（经 Worker Secret 注入密钥）
```

交付时写清：哪些层已部署验证、哪些层仍由用户验收（ChatGPT 连接、自然语言测试）。
