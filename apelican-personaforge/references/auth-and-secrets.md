# 认证与 Secret 边界（4.0：默认非 OAuth）

## 决策顺序：先问三个问题

| 问题 | 答案全为「否」 | 任意为「是」 |
|---|---|---|
| 用户数很多或公开发布？ | → 走下面的**默认路径** | 才考虑 OAuth 2.1 |
| 不同用户访问各自的数据？ | | |
| 需要独立的撤销 / 刷新 / 审计？ | | |

默认路径（推荐，占 90% 的场景）：

```text
ChatGPT 端：No authentication（noauth）
服务端：    URL 路径携带随机令牌（/u/<256位随机令牌>/mcp），Worker 校验 LINK_TOKEN
```

- ChatGPT 不发送任何认证头，但仍然只有拿着完整链接（含令牌）的人能调用；
- 令牌只以 SHA-256 摘要形式保存（本技能模板直接对比常量时间字符串，部署时可选择进一步哈希）；
- 链接泄露时重生成令牌并覆盖 `LINK_TOKEN` Secret，旧链接立即失效；
- 这一模式不需要配置授权服务器、不需要注册客户端、不会遇到 ChatGPT 端 OAuth 验证失败的问题。

## 为什么默认不选 OAuth

OAuth 2.1 在 Cloudflare Worker 上自建意味着：授权服务器 metadata、客户端注册、PKCE、audience、scope、刷新和撤销全部要到 OpenAI 侧验证通过。实操中它：

- 实现量大（远超一次部署的其余部分）；
- ChatGPT 端验证经常失败，失败原因不明确，排查成本高；
- 对个人自用、小圈子、数据不分的场景没有收益。

只有当「多数用户各自的数据」「公开发布给大量用户」「必须撤销与审计」成立时，OAuth 的收益才超过成本。此时：**明确告知用户更麻烦、可能验证失败**，单独核对官方文档，并准备降级路径（先用默认令牌路径上线，再评估 OAuth）。

## 三类信息必须分离

1. **上游凭据**：API Key、Bearer、Client Secret → 只进 Cloudflare Worker Secret（`UPSTREAM_KEY` 或透传配置），不进代码、回复、日志；
2. **插件入口认证**：ChatGPT 端怎么连 → 默认 `noauth` + 路径令牌（见上）；
3. **普通配置**：来源 ID、超时、结果上限、工具描述 → 可写在代码/文档。

ChatGPT 不需要知道上游凭据；上游服务也不需要知道你的链接令牌。

## 收到真实凭据时（铸造模式的常态）

铸造模式需要用户提供 `CF_API_TOKEN`、上游密钥等真实凭据。处理规则：

- 仅用于本次部署与验证请求，用完即清；不写入技能文件、GitHub、日志、审计输出或回复正文；
- 命令参数、URL 中不出现密钥值；Secret 经 API 请求体或交互式输入传递；
- `CF_API_TOKEN` 本身建议用后即删（引导用户到 Cloudflare 后台删除）；
- 上游密钥粘贴进过对话时，交付时附一句「建议在上游后台轮换」；
- 不把「已提醒轮换」写成「已经轮换」。

## OAuth 方案至少标明的要素

若最终确需 OAuth：protected-resource metadata、授权服务器 metadata、PKCE、客户端识别/注册、audience、scope、运行时挑战、刷新与撤销。实际实现以最新官方文档为准，本技能不提供「已验证成功」的承诺。
