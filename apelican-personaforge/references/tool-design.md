# 工具面设计（自动压缩）

铸造机自动把用户接口变成 ChatGPT 好选的工具面。原则：**少而准**。

## 每个工具

- `name`：稳定、动作开头，例如 `search_documents`；
- `title`：供人阅读；
- `description`：说明完成什么、何时使用、何时不用、重要限制和返回内容——ChatGPT 靠它选工具，写不清等于没写；
- `inputSchema`：参数说明格式、单位、默认值和范围；
- `outputSchema`：需要结构化结果时使用对象根；
- `annotations`：与真实读取、写入、删除、联网和幂等行为一致；
- `securitySchemes`：默认 `[{ "type": "noauth" }]`（ChatGPT 不另走 OAuth，服务端令牌由 URL 路径承担）。

## 工具压缩

- 相似工具优先合并为任务型工具（例：10 个不同数据库的查询合并成 `search_documents(query, source?)`）；
- 不拿固定数字冒充平台上限；当工具数量、相似描述或 schema 总量已经让模型选择准确率下降，就压缩；
- 大目录场景压缩为两个入口：目录搜索 + 静态 allowlist 受控只读执行；
- 搜索结果不授予执行权限；名称正则只能额外拒绝疑似写工具，不能自动放行；
- 上游新增工具不会因为目录刷新而自动获得权限。

## 副作用分层

- 只读工具：默认保留，进 allowlist；
- 写操作：逐个注册、单独命名（`create_` / `update_` / `delete_`），必须在交付说明里明确列出，不能藏进通用执行器；
- 付款、对外发送（发信、发帖）：单独设计，交付时按高风险能力提示用户；
- 无法从名称判断副作用的，标「待核验」，不默认只读。

## 结果

- 协议错误与工具错误分开（`isError`）；
- 声明 `outputSchema` 时同时规划 `structuredContent` 和模型可读 `content`；
- 分页、截断和下一页位置明确；
- 没有真实 canonical URL 时不伪造引用链接；
- 错误信息不包含堆栈、内部 URL、认证头、密钥或私人正文。

## 方案审阅输出（设计模式用）

用表格列出：工具名、目标、输入、输出、副作用、认证、是否保留、理由。没有证据判断副作用时标记「待核验」。
